# Handling Rust Review Comments: "No Shell Commands in IO Paths"

When an upstream Rust reviewer objects to shell-out in hot/IO paths (e.g.
`"IO 路径上不要依赖系统 shell 命令"`), don't argue — replace with native
Rust. Worked example: EasyTier PR #2424 (MagicDNS), replacing `ip addr
add/del` + `resolvectl` calls.

## Strategy (in order of preference)

1. **Reuse the project's existing abstraction first.** EasyTier already had
   `IfConfiguerTrait` in `easytier/src/common/ifcfg/mod.rs` with netlink
   implementations (`add_ipv4_ip` / `remove_ip`). Shell `ip addr add/del`
   became two netlink calls — no new dependency, cross-platform for free.
   Search the codebase for existing trait/abstraction layers BEFORE adding
   new crates.

2. **D-Bus via `zbus` for systemd services.** `resolvectl dns/domain` talks
   to `org.freedesktop.resolve1.Manager` — call the same interface directly:
   - `SetLinkDNS(ifindex, [(AF_INET, octets)])` — real signature is `ia(iay)`
     = TWO args (ifindex i32, then array of (family i32, byte-array)). A
     3-tuple `(ifindex, 0i32, ns)` compiles but fails with InvalidArgs at
     runtime — verified against live systemd (EasyTier PR #2424, 2026-08-03).
   - `SetLinkDomains(ifindex, [(domain, routing_only_bool)])` — `ia(sb)`.
   - ifindex from `libc::if_nametoindex` (nix::libc).
   - **Probe the service, not the bus.** `Connection::system().is_ok()` only
     proves a D-Bus daemon exists — resolve1 may be absent. Call
     `org.freedesktop.DBus.Peer.Ping` on the resolve1 object path (every
     object implements Peer, so a reply proves the service is registered):
     ```rust
     conn.call_method(Some(RESOLVE1_SERVICE), RESOLVE1_PATH,
                      Some("org.freedesktop.DBus.Peer"), "Ping", &()).is_ok()
     ```
     ⚠️ ROUND-2 GOTCHA: connection success is NOT a resolver probe — reviewers
     will push back with "不是所有 linux 都有 systemd". See "Round 2: not
     every Linux has systemd" below.

3. **Feature-gate the dependency.** `zbus = { version, optional = true,
   features = ["blocking"] }` under `[target.'cfg(target_os = "linux")'.dependencies]`,
   then `dep:zbus` in the relevant feature (e.g. `magic-dns`). NB: zbus 5.x
   has NO `proxy` feature — don't add it, Cargo errors.

## Round 2: not every Linux has systemd

`org.freedesktop.resolve1` is systemd-resolved-specific. Alpine, Gentoo/OpenRC
and other non-systemd distros have no such interface — and a plain
`Connection::system()` probe is NOT enough: the system D-Bus bus exists on many
non-systemd systems, so the connection succeeds and `SetLinkDNS` fails with
UnknownMethod/UnknownObject, silently no-oping DNS config.

Handle it as a detection chain with a file-based fallback (Tailscale's design —
see `tailscale-linux-dns-design.md`):

1. Detect the resolver in charge: read `/etc/resolv.conf` header + check it
   points at 127.0.0.53 (systemd-resolved stub) or `resolve` in
   `/etc/nsswitch.conf`. Header alone is not proof (tailscale issue #2136).
2. systemd-resolved in charge → D-Bus SetLinkDNS/SetLinkDomains (keep the
   round-1 implementation; supports per-domain routing).
3. Otherwise → direct mode: back up `/etc/resolv.conf` (rename to
   `resolv.conf.easytier.bak`), atomically write `nameserver <fake_ip>` +
   `search <zone>` with a `# generated by easytier` marker; on `close()` restore
   ONLY if the current file still carries our marker (ownership check — never
   clobber someone else's newer config).
4. Direct mode cannot do split DNS — `match_domains` degrade to search domains
   (same limitation as the darwin file-based configurator).

## Pitfalls hit

- **Dead imports from the PR branch itself**: the original PR branch failed
  to compile due to unused `pnet` imports. Remove them; don't assume PR
  branches build.
- **`Ipv4Inet::new` returns Result** — `.expect("...")` with a justification
  string, not a blind unwrap panic risk.
- **Struct-field additions break other cfg targets' tests** (darwin test
  constructs `OSConfig` literally) — add `interface_name: None` there too.
- **Controller API ≠ node online state** (if the PR touches network config):
  verify against the real daemon, not the config API.
- **compile-pass ≠ runtime-OK for D-Bus.** Method names and arg signatures
  are NOT checked by cargo. `ListLinks` is NOT part of resolve1.Manager — a
  probe using it returns false on every system while compiling cleanly.
  Verify the real interface BEFORE coding:
  `busctl --system introspect org.freedesktop.resolve1 /org/freedesktop/resolve1`
  lists actual methods with signatures (has `.Ping`, `SetLinkDNS ia(iay)`,
  `SetLinkDomains ia(sb)` — no ListLinks).
- **dbus-send can't express complex types** like `a(iay)` ("Unknown type").
  Use gdbus:
  `gdbus call --system --dest org.freedesktop.resolve1 --object-path
  /org/freedesktop/resolve1 --method org.freedesktop.resolve1.Manager.SetLinkDNS
  1 "@a(iay) [(2, [byte 0x7f, 0x00, 0x00, 0x01])]"`
- **Non-root gdbus/dbus calls hit polkit** (`InteractiveAuthorizationRequired`).
  The real runtime (TUN setup) runs as root — test with sudo. A `LinkBusy:
  Link lo is loopback device` error is a SUCCESS signal: the signature parsed
  and the call was attempted; lo just rejects DNS config. Test on a real
  non-loopback interface and restore afterwards (`SetLinkDNS <ifindex> []`).
- **Restore system state after D-Bus experiments** — clearing enp1s0's DNS
  via SetLinkDNS left it empty; NetworkManager re-pushed it on `nmcli con up`.
  Check `resolvectl dns <iface>` before/after.

## Verification (always both)

```bash
cargo check -p <crate> --features <feature>   # the changed path
cargo check -p <crate>                        # default features unaffected
```

MagicDNS integration tests failing with `PermissionDenied` on TUN = local
permission issue, NOT your change. Say so in the PR comment.
